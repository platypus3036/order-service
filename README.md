# 📦 Order-service

### 🔖 서비스 개요








- **주제**: 주문 처리 및 주문 이벤트 발행을 담당하는 서비스  
- **주요 역할**:
  - 사용자 주문 요청 수신 및 처리
  - 주문 검증 및 상태 저장
  - 유저 서비스와 연동하여 잔액 및 보유 종목 검증
  - RabbitMQ를 통한 주문 이벤트 발행 (`order.created`)
  - 체결 결과 이벤트 수신 (`order.decreased`, `account.decreased`)
  - 회사 정보(CompanyCode) 제공 및 연동
  - 체결 결과 기반 거래 내역(TradeHistory) 저장 및 관리

### 🔗 주요 기능








#### 1️⃣ 주문 생성 및 처리
- 사용자로부터 주문 요청을 수신
- 가격 유효성, 보유 자산 검증을 위한 이벤트 발행
- 주문 데이터를 생성하고 상태 저장

#### 2️⃣ 주문 데이터 관리
- 주문 정보는 DB에 저장 및 관리됨
- 체결 결과 수신 시 주문 수량 감소 및 상태 업데이트

#### 3️⃣ 주문 검증 및 이벤트 발행
- 유저 서비스와의 통신을 통해 잔액 및 보유 주식 검증 요청
- 검증 결과에 따라 `order.created` 이벤트 발행

#### 4️⃣ 체결 결과 수신 및 반영
- Matching 서비스로부터 체결 결과 이벤트 수신
- 체결 수량에 따라 주문 상태 변경
- 거래 내역 데이터 생성 및 저장

#### 5️⃣ 회사 정보 조회
- CompanyCode 기준으로 종목 관련 정보 제공
- 주문 처리 시 종목 정보 검증 및 활용

#### 6️⃣ 거래 내역 관리
- 체결 완료 시 `TradeHistory` 기록 생성
- 사용자별, 종목별, 기간별 체결 내역 조회 기능 제공

### 🌈 개선 사항

#### 1️⃣ 주문 ID 생성 방식 개선 - <ins>저장 공간 절약 및 고속 삽입 성능 확보</ins>

**📌 문제 상황**

- **분산 환경 확장성 저해**: 여러 데이터베이스 인스턴스 또는 샤딩 환경으로 확장 시, 중앙 집중적인 ID 생성 방식은 충돌 방지를 위한 추가 로직이 필요하거나 ID 채번 서버 도입 등 복잡성을 야기하고 병목 지점 가능성
- **성능 병목 가능성**: 대량의 데이터 삽입 작업 시, `AUTO_INCREMENT`는 테이블 레벨 락 또는 내부적인 락 메커니즘으로 인해 동시 삽입 성능을 저하 가능
- **ID 예측 가능성**: 순차적으로 증가하는 ID는 다음 생성될 ID를 쉽게 예측할 수 있어, 특정 엔드포인트에 대한 추측성 공격이나 정보 유추 시도 등의 보안 취약점 될 가능성 다수

**✅ 개선 방향**

- **분산 환경에서의 고유성 보장**: TSID는 타임스탬프와 랜덤 노드(또는 시퀀스) 정보를 조합하여 생성되므로, 여러 서버 또는 애플리케이션 인스턴스가 동시에 ID를 생성하더라도 높은 확률로 고유성을 보장
- **저장 공간 효율성 증대 및 인덱싱 성능 향상**: TSID는 일반적으로 64비트 정수(Long 타입, 8바이트)로 표현 -> 128비트를 사용하는 UUID(16바이트)에 비해 저장 공간을 약 50% 절약할 수 있으며, 데이터베이스 인덱스 크기를 줄여 검색 및 정렬 성능에도 영향
- **시간순 정렬 가능성**: TSID는 생성 시간 정보를 포함하므로, 별도의 `created_at`과 같은 타임스탬프 필드 없이도 ID 자체로 시간순 정렬이 가능하여 데이터 조회 및 분석에 유리
- **고속 삽입 성능**: 애플리케이션 레벨에서 ID를 생성하므로 데이터베이스의 ID 생성 메커니즘에 대한 의존성을 줄이고, 데이터베이스 부하를 경감시켜 삽입 성능 향상에 기여

#### 2️⃣ 종가 데이터 인메모리 캐싱 적용 - <ins>DB 부하 약 24% 감소</ins>

**📌 문제 상황**
- 주식 주문 처리 시, 사용자가 입력한 주문 가격의 유효성을 검증하기 위해 해당 종목의 전일 종가 정보가 필요
- 기존 시스템에서는 이 종가 정보를 **매 주문 요청마다 데이터베이스에서 조회**
   -**반복적인 DB 접근으로 인한 성능 저하**: 특히 동시 주문이 많은 상황에서 동일한 종목의 종가 정보를 반복적으로 조회하는 것은 불필요한 DB I/O를 발생시키고 응답 시간을 지연.
   - **DB 부하 가중**: 서비스가 성장하여 관리하는 종목 수가 900개 이상으로 증가함에 따라, `findAll`과 같은 전체 조회나 빈번한 단일 조회가 누적되어 데이터베이스에 상당한 부하를 주었고, 이는 전체 시스템의 성능 병목 지점으로 작용

**✅ 개선 방향**
-   종가 데이터는 장 마감 후 다음 날 개장 전까지는 변동이 없는 데이터라는 특성에 착안하여, **인메모리 캐싱 전략**을 적용
   -   **서버 구동 시 종가 데이터 캐싱**: 애플리케이션 서버가 시작될 때, 모든 활성 종목의 전일 종가 데이터를 데이터베이스에서 한 번 조회하여 내부 메모리(예: `ConcurrentHashMap`과 같은 스레드 안전한 자료구조)에 캐싱.
   -   **주문 검증 시 메모리 우선 조회**: 이후 주문 요청이 들어오면, 종가 정보가 필요한 경우 데이터베이스를 직접 조회하는 대신 캐시된 인메모리 데이터에서 즉시 조회.
   -   **데이터 일관성 유지**: 종가 데이터는 일별로 고정되므로, 서버가 재시작되거나 일일 배치 작업을 통해 데이터가 갱신될 때까지 캐시된 데이터를 안전하게 사용 가능. (필요시, 특정 시간에 캐시를 무효화하고 재로딩하는 전략도 고려 가능)
    -   **DB 부하 감소 효과**: 이 개선을 통해 DB 조회 횟수를 획기적으로 줄여, DB 부하를 약 24% 감소시키는 효과를 확인했습니다. 이는 주문 처리 속도 향상 및 시스템 전반의 안정성 증대에 기여.

#### 3️⃣ 서버 간 통신 속도 개선 - <ins>gRPC 적용으로 응답 시간 단축</ins>

**📌 문제 상황**
-   기존의 모놀리식 아키텍쳐에서 MSA로 전환 시, 서버간 통신에서 병목 지점 발생
   -   **연결 수립 오버헤드**: HTTP/1.1은 요청마다 TCP 연결을 새로 맺거나(Keep-Alive를 사용하더라도 한계 존재) 관리하는 데 비용이 발생하며, 특히 잦은 통신 시 3-way handshake 과정이 누적되어 지연을 유발.
   -   **텍스트 기반 메시징 및 직렬화 비용**: 주로 JSON 형식을 사용하여 데이터를 주고받았는데, 이는 바이너리 프로토콜에 비해 메시지 크기가 크고, 직렬화/역직렬화 과정에서 CPU 자원을 소모하여 성능에 부담
   -   **헤더 중복 및 크기**: HTTP/1.1은 매 요청/응답마다 상대적으로 큰 크기의 헤더를 텍스트 형태로 전송하여 네트워크 대역폭을 비효율적으로 사용
   -   **HOL (Head-of-Line) Blocking**: 하나의 커넥션에서 요청은 순차적으로 처리되므로, 특정 요청 처리가 지연되면 동일 커넥션을 사용하는 후속 요청들도 대기

**✅ 개선 방향**
- 이러한 통신 비효율을 개선하고 서비스 간 응답 속도를 향상시키기 위해, **HTTP/2 기반의 고성능 RPC(Remote Procedure Call) 프레임워크인 gRPC**를 도입.
   - **HTTP/2 기반의 효율적인 통신**
      - **멀티플렉싱(Multiplexing)**: 단일 TCP 연결 상에서 여러 요청과 응답을 병렬적으로 스트리밍하여 HOL Blocking 문제를 해결하고 연결 재사용성을 극대화.
      - **헤더 압축(HPACK)**: 헤더 정보를 효과적으로 압축하여 전송 데이터 크기를 줄이고 네트워크 효율성을 높임.
      - **서버 푸시(Server Push)**: 클라이언트가 요청하지 않은 리소스도 서버가 미리 전송할 수 있어 초기 로딩 속도를 개선.
   - **Protocol Buffers (Protobuf) 사용**:
      - **효율적인 직렬화**: 스키마 기반의 바이너리 직렬화 포맷인 Protobuf를 사용하여 JSON 대비 데이터 크기가 작고 직렬화/역직렬화 속도가 매우 빠름.
      - **엄격한 스키마 관리**: `.proto` 파일을 통해 서비스 인터페이스를 명확하게 정의하고, 다양한 언어의 클라이언트/서버 코드를 자동으로 생성하여 개발 생산성을 높임.
